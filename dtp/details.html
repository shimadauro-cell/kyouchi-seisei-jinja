AIで作った同人誌DTPソフトの作り方

開発の進め方

先に「完成の判定基準つきの仕様書」を作り、AI はそれを正本として段階的に実装しました。人は各段階の終わりに画面で確かめて、次へ進むかどうかを決めます。

  1. 仕様を詰める（人＋AI、チャット）：GPT版とClaude版の仕様書を統合し、「統合仕様書 v2」を Claude Docs にまとめた。要求に番号、受け入れ試験 T01〜T24、段階 P0〜P5、未決事項の一覧。
  2. 技術の選定（AIが比較、人が決定）：複数案を比べ、人が「案A：Electron＋TypeScript」を選んだ。
  3. P0 は「一番危ない所」の試作から：縦組・ルビ・日本語入力（IME）、画面とPDFの一致を最初に確かめた。
  4. 段階ごとに実装 → 自動テスト → 画面の自動確認 → Git に記録 → 人への確認手順：人は「どこを押して、何が見えれば合格」の手順で確かめて OK／NG を返す。
  5. 夜間は自走：「寝るので進めれるだけ実装して」の一言で、P4〜P5 を一気に実装。朝にまとめて報告と確認手順を渡した。
  6. 実際の本で試す：生成AIで作った40ページの情報誌と、二段組の小説をこのソフトで組み直し、不具合を実戦で見つけた。
  7. 別のAIにレビューさせる：GPT にコードをレビューさせ、指摘を Claude が「本当に起きるか」再現してから修正。

仕様書には「依頼者はコードを書かない」「説明は専門用語を避ける」「仕様にない機能は追加しない、無断で範囲を削らない」という進め方そのものも書いてあり、Claude はそれをプロジェクトの指示書（CLAUDE.md）に写して守りました。

Claude の処理の仕方

Claude は「作る」より「確かめる」に多くの手間を使いました。人が画面を見る前に、AI 自身がテストと画面の写真で合否を確かめ、ダメなら直してから報告します。

  • 仕様書を正本にする：仕様書（Claude Docs）を読み、要求ごとに ✅／△／⬜ を付けた対応表（SPEC.md）を段階ごとに更新。仕様にない追加は「依頼者の指示で追加」と日付つきで記録。
  • 段階を小さく切る：1段階は「人が画面で確かめられる単位」。段階の終わりに必ず Git に記録し、変更履歴（CHANGELOG）を人の言葉で書く。
  • 中身の自動テスト：組版・PDF・PNG・保存などは vitest で確かめる。仕様書の受け入れ試験（T04・T14 など）をそのままテストの名前にした。
  • 画面を自分で操作して見る：アプリに「手順ファイルを渡すと、クリック・キー入力・画面写真を自動で行う」仕組みを入れ、Claude が写真を見て崩れを探す。後にこれを「合否を判定する画面の自動テスト（E2E）」に発展させた。
  • 直したと言う前に、直す前のコードでテストが落ちることを確かめる：レビュー指摘の修正では、修正前のコードに戻して「テストが失敗する」ことを確かめ、不具合を本当に捕まえているかを検証。
  • テストが間違っているのか、コードが間違っているのかを分ける：失敗を見たら先に原因を調べる。テストを通すためにコードを曲げない。
  • 安全の線を守る：ファイルのダウンロードや外部への送信は人の許可を得てから。夜間の自走中でも、印刷の色の基準ファイル（Japan Color）は勝手に取得せず、Windows 同梱の代わりで進めて朝に許可を求めた。
  • 長い作業は「引き継ぎ」でつなぐ：会話が長くなると記憶が要約される。そのため、状態はリポジトリの書類（ROADMAP・SPEC・TEST_PLAN・CLAUDE.md）と Git に残し、記憶に頼らない。
  • 大きな変更は「差し替え用の小さなスクリプト」で：複数ファイルにまたがる変更は、「この文字列が1回だけあることを確かめてから置き換える」小さな Python スクリプトで行い、置き換えの漏れや二重適用を防いだ。

設計

一番大事にしたのは「画面で見たとおりに印刷される」ことです。そのため、文字の組み方は1か所でだけ計算し、その結果（描画命令のリスト）を画面・PNG・PDF が共通で使います。出力ごとに組み直すと、改行位置がずれるからです。

層中身動く場所
文書モデル本・ページ・枠・文字・素材。座標はすべて mmどこでも（画面にも Node にも依存しない）
組版エンジン縦組・横組、ルビ、縦中横、禁則、約物の詰め、段組、流し込みどこでも（自作）
描画命令リスト「この字形をここに、この画像をここに」の一覧（buildPageDisplay）どこでも
出力画面（Canvas）・PNG・PDF の3つが、同じリストを描く画面はアプリ、PNG・PDF は裏側（Node）
色ICC プロファイルで RGB→CMYK・グレー・2階調どこでも（自作）
編集操作すべて「古い文書→新しい文書」を返す関数。元に戻すは文書の写しを積むだけどこでも
画面（React）リボン、ページ一覧、右の欄、ダイアログElectron の画面側
ファイル・書き出し保存、自動保存、フォントの読み込み、PDF・PNG の書き出しElectron の裏側

守った原則：

  1. 画面・PNG・PDF は同じ描画命令から描く。PDF を別の描画ソフト（pdf.js）で画像にして PNG と画素単位で比べ、違う画素が 1% 未満であることを自動テストにした。
  2. 中心部（core）は画面にも OS にも依存させない。だから画面を開かずに、組版も書き出しも高速にテストできる。
  3. 編集はすべて「新しい文書を返す」形。元に戻す・自動保存・マスターや表紙の編集が簡単になる。
  4. マスターや表紙は「仮の文書」で編集。表紙の見開きを1ページの文書にして、普通の編集画面をそのまま使い回す。編集後に本物へ書き戻す。
  5. 壊れにくい保存。一時ファイルに書いて読み戻し、確かめてから置き換える。複数ファイルの書き出しは、全部そろってから一度に置き換える。
  6. 文書ファイルに画像を同梱（ZIP 形式の .dtpbook）。別のフォルダーや PC に移しても画像が欠けない。

採用したもの・採用しなかったもの

既製の部品は「フォントを読む」「圧縮する」「画像を描く」などの土台だけにしました。日本語の組版、PDF の書き出し、色の変換というこのソフトの芯は、画面と PDF を完全に一致させるために自作しています。

分野採用したもの採用しなかったもの・理由
アプリの土台Electron 44・React 19・TypeScript・Vite（案A）他の候補と比較し、依頼者が案Aを選択。日本語入力（IME）・描画・配布のしやすさを重視
縦組・ルビの組版自作の組版エンジンブラウザの縦書き（CSS writing-mode）は、PDF と同じ改行・同じ位置を保証できない
フォントfontkit（字形・縦書き字形・サブセット）縦組用の字の高さの表（vmtx）だけ不具合があり、そこは自分で読む
PDF 書き出し自作（日本語フォントの埋め込み、CMYK、トンボ、画像の無劣化の埋め込み）既製の PDF ライブラリは、縦組・ページごとの色・CMYK の扱いで制約が多い。pdf-lib・pdf.js は「テストで開いて確かめる側」だけに使う
色の変換自作の ICC エンジン仕様書が想定した LittleCMS は、ネイティブの部品が増えて配布が重くなるため見送り
画像の変換・描画@napi-rs/canvas、fflate（圧縮）—
印刷の色の基準Windows 同梱のプロファイル＋利用者が追加Japan Color 2001 Coated の自動ダウンロード（許可なしに外部から取得しない）
テストvitest、自作の画面自動操作（Electron に組み込み）Playwright などの外部ツール（追加のダウンロードが要るため、アプリ自身に操作の仕組みを入れた）
配布インストール不要のポータブル版、rcedit（exe のアイコン）自動更新・利用状況の送信（仕様で初期版に含めない）
通信なし（完全オフライン）クラウドの AI 解析など。画像や原稿を外へ送らない。綴りの確認機能も止めた
画像素材アイコンは依頼者が GPT で生成、ボタンの絵は Claude が線画（SVG）で描画ボタン約60個を画像生成で作るのは、絵柄がそろわず小さくすると潰れるため見送り
太字・フチ字形の輪郭を線でなぞる太字のフォントへの切り替え（太字の書体が入っていないフォントでも使えるように）

品質の確かめ方

「人が全部確かめる」のは無理があるため、確認を三層に分けました。人の手で確かめる項目は、75項目から 8項目まで減りました。

層何を確かめるか数
中身の自動テスト組版（禁則・ルビ・縦中横）、保存を 10 回繰り返しても不変、PDF の寸法・フォント埋め込み、PDF と PNG の画素一致、色変換、プリフライト、復旧、性能（32ページ・画像100点）160件
画面の自動テスト（E2E）アプリを起動し、本を作る・文字を打つ・画像を落とす・枠を動かす・書き出す・強制終了から復旧、までを操作。書き出したファイルは別のプログラムで開いて判定。外部への通信が 0 件であることも毎回確認95項目（約4分）
人の手での確認日本語入力（IME）、エクスプローラーからのドラッグ、PDF の見た目の印象、実際に印刷して折る、印刷所への入稿8項目

このほかに、実際の本を2冊組んで不具合を探した（例：表紙とマスターの画像が保存されていなかった）、別の AI（GPT）のコードレビューで重大な4件を見つけた、という確認もしています。オフライン動作は、「ネットを遅断して起動」「アプリ内の通信の記録」「OS 側からの接続の見張り」の3つで確かめました。

うまくいったこと・つまずいたこと

AI で開発する人への一番のヒントは、「完成の基準を先に文章で決め、AI に自分で確かめさせる」ことです。

うまくいったこと

  • 受け入れ試験つきの仕様書：「本文32ページ・紙叚0.1mmで背幅1.6mm」のように合否が数字で書かれていると、AI がそのままテストにできる。
  • 「一番難しい所」を最初に試作：縦組・ルビ・日本語入力を P0 で确かめたので、後で土台から作り直すことがなかった。
  • 人の確認は「何を押して何が見えれば合格」の形で：コードを読めなくても判定できる。
  • 画面を AI 自身が操作して写真で見る：「動くはず」で報告せず、写真で崩れを見つけてから直せた。
  • 別の AI にレビューさせる：作った AI が見落とす穴（書き出しの失敗時に前回の出力が消える、PDF だけ不透明度が崩れる、など）を別の視点で見つけられた。
  • 実際の本を組んでみる：テストでは通っていた「表紙の画像が保存されない」不具合は、本を組んで初めて見つかった。

つまずいたことと対処

つまずき対処
シェルの中で日本語や「\」を含むコードを置き換えると、文字が化ける・壊れる置き換えはファイルに書いたスクリプトで行い、「1回だけ見つかること」を確かめてから実行
画面の拡大率（114%）で、自動操作のクリック位置がずれる座標ではなく「ボタンの文字」や「ページ上の mm」から位置を計算する仕組みにした
テストが落ちたとき、テストが悪いのかコードが悪いのか紛らわしい原因を調べてから直す。直した後は、直す前のコードでテストが落ちることも確かめる
会話が長くなると、AI の記憶が要約されて細部が消える状態をリポジトリの書類と Git に残し、記憶に頼らない
自動操作の確認で、依頼者の「最近のファイル」や設定を汚してしまった自動テスト中は設定の置き場所を別のフォルダーに切り替えた
生成AIの画像は印刷には粗い（A5 全面で約180dpi）プリフライトで知らせる。文字は本物の文字に置き換えるとくっきり印刷できる（バージョン2の構想へ）

これから（バージョン2の構想）

次は「生成AIで作ったページ画像を読み込むと、文字・写真・背景に分解して編集できる素材にし、人が少し直すだけで入稿できる」機能を検討しています。今回、AI が40ページの情報誌を手作業で組み直したのが、その試作にあたります。

  1. AIなしの道具：下絵として読み込む・選んだ範囲を切り抜いて素材にする・範囲の文字を消す
  2. 範囲を選んで文字を読み取る：Windows に入っている文字読み取り（OCR）を使い、オフラインのまま文字枠にする
  3. ページ全体を自動で分解：同梱する小さな AI モデルで、文字・図・背景を一気に配置
  4. （検討中）外の AI による高精度の解析：初期設定はオフ、使うたびに確認。「完全オフライン」の仕様をどこまで変えるかが論点

文字を本物の文字に置き換えると、生成AIの画像の粗さに関わらず文字がくっきり印刷されます。今回作った「文字起こしの正解データ」は、読み取りの精度を数字で測る試験にそのまま使えます。
